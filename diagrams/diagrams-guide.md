# Diagram Guide: Data Mesh Reference Architecture for NOAA Fisheries

This guide documents the 17 diagrams produced for *A Data Mesh Reference Architecture for NOAA Fisheries*. Each entry provides a title, a brief caption situating the diagram in the paper's argument, and a concise walkthrough narrating the diagram from start to end as if explaining it to a colleague. Diagrams are listed in the order they appear in the paper.

---

### Diagram 1: Electronic Monitoring Data Product Flow (Section 5.2)

**Caption:** Illustrates the flow of Electronic Monitoring data from upstream sources through the Fishery Monitoring domain to downstream consumers, with platform services enforcing governance across the entire pipeline.

**Walkthrough:** Starting on the left, upstream data sources feed into the system — raw video footage enters Cloud Storage, EM trip reports arrive in BigQuery, and an ingestion API on Cloud Run accepts incoming data from service providers. These streams converge into the Fishery Monitoring domain, shown as a bordered group in the center, where the EM Data Product sits as the centerpiece in BigQuery. Surrounding it within the domain are Dataplex for quality rules and Data Catalog for metadata and discovery. From the domain, dashed arrows fan out to three downstream consumers on the right: Stock Assessment queries aggregated catch composition, Protected Species filters for interaction events, and Enforcement accesses vessel-level trip details. Across the bottom, a set of platform services — Cloud IAM for row-level security, Cloud Monitoring for SLO dashboards, and Cloud DLP for PII detection — connect upward to the EM Data Product with dashed "enforcement" lines. The diagram shows that the data product is never exposed raw; every consumer sees a governed, access-controlled view enforced by the platform.

### Diagram 2: Internal Anatomy of the EM Data Product (Section 5.2)

**Caption:** Reveals the internal structure of the EM data product across three layers — storage, interface, and governance — with six descriptive storage components that follow the real EM workflow from capture through processing to publication.

**Walkthrough:** The diagram is arranged in three horizontal bands inside a solid boundary labeled "EM Data Product." The top band, the storage layer, displays six uniform cards in a single row following the natural EM workflow. The first three cover capture and ingestion: Trip Metadata records vessel ID, timestamps, region, fishery type, and gear configuration in BigQuery; Raw Video and Sensor Data stores camera footage, gear telemetry, GPS tracks, and hydraulic sensor readings in Cloud Storage; and Reviewer Notings captures human reviewer annotations, video segment indices, and initial species observations in BigQuery. The next three cover processing and publication: Logbook Reconciliation cross-references captain-reported catch with EM observations and flags discrepancies; Species Identification records family or species-level IDs with confidence ratings, validated against the authoritative AFS taxonomy; and Trip Report (Published) is the unified, quality-verified output containing catch composition, discards, and protected species interactions. A workflow annotation beneath the storage cards reads "Capture & Ingestion → Processing & Reconciliation → Publication," reinforcing the progression. The middle band, the interface layer, exposes two consumption paths: a REST API on Cloud Run for programmatic read access and a SQL Query Interface on BigQuery for analytical consumers. The bottom band, the governance layer, provides the product's quality and access guarantees: the Data Contract in Data Catalog specifies schema v1.2, SLOs, versioning policy, and access rules; Quality SLOs in Dataplex enforce completeness above 99% and species accuracy above 95% at family level and 90% at species level; and Row-Level Access via Cloud IAM enforces MSA §402(b) confidentiality restrictions on vessel-level data.

### Diagram 2b: EM Data Product Definition (Section 5.2)

**Caption:** Provides a higher-level conceptual view of the EM data product as a bounded unit defined by its schema, contract, metadata, access methods, and downstream consumers.

**Walkthrough:** At the center sits a labeled box representing the EM Data Product itself. Arrayed around it are five defining facets. On the top-left, the dataset schema lists the core tables — trip metadata, video footage notings, sensor data, logbook reconciliation, and species identification records — each with their BigQuery DDL patterns. On the top-right, the data contract enumerates the formal guarantees: schema v1.2, completeness above 99%, species accuracy thresholds, 30-day timeliness, a 90-day deprecation notice policy, and row-level access rules. The metadata block on the bottom-left captures descriptive information — collection methodology, QA procedures, Data Product Owner contact, and temporal/spatial coverage — all registered in Data Catalog. Across the bottom, two access methods are shown: BigQuery SQL for analytical queries and a REST API for programmatic access. Finally, on the bottom-right, three consumer icons represent the downstream use cases: stock assessment aggregation queries, protected species interaction filtering, and enforcement vessel-level compliance checks. The diagram reinforces that a data product is not just a dataset; it is a defined unit with explicit structure, quality guarantees, discoverable metadata, governed access, and documented consumption patterns.

### Diagram 4: Data Product Creation Workflow (Section 5.3)

**Caption:** Sequences the automated steps a Data Product Owner follows to create a new data product — from template execution through sandbox validation to production discovery.

**Walkthrough:** The diagram is a top-to-bottom flowchart. Step 1: the DPO executes a platform-provided Terraform template. Step 2: Cloud Build validates the schema and runs integration tests. From here, the workflow branches into five parallel provisioning steps — BigQuery dataset creation, IAM policy application, Data Catalog registration, Dataplex quality rule deployment, and Cloud Monitoring SLO dashboard setup — all happening simultaneously. These converge into Step 8: sandbox validation in an isolated environment where test data and real data are guaranteed never to mix. Once validated, Step 9: the DPO promotes the data product to production. The final step shows the Data Catalog entry becoming discoverable by consuming domains like Stock Assessment and Enforcement. Platform automation steps 2 through 7 are grouped in a dashed boundary, and step 8 is in its own sandbox boundary, emphasizing that the DPO never touches individual services — the platform handles everything from template to publication.

### Diagram 5: NIST 800-53 Control Inheritance Model (Section 5.4)

**Caption:** Illustrates the three-tier control inheritance strategy — GCP FedRAMP to platform team to DPO — showing how 60–70% of NIST controls are inherited, dramatically reducing per-product compliance burden.

**Walkthrough:** The diagram is built bottom-to-top, with the foundation at the base. Layer 1, the bottom band labeled "FedRAMP Common Controls," represents GCP's authorized infrastructure providing physical security, hypervisor isolation, and network segmentation. Inheritance arrows point upward to Layer 2, the middle band labeled "Platform ATO — Hybrid Controls," where the NMFS platform team implements six specific NIST controls mapped to GCP services: AC-3 Access Enforcement via Cloud IAM, AU-2 Audit Logging via Cloud Logging, SC-7 Boundary Protection via VPC Service Controls, SI-10 Input Validation via Dataplex, SC-13 Cryptographic Protection via Cloud KMS, and RA-5 Vulnerability Monitoring via Security Command Center. More inheritance arrows point upward to Layer 3, the top band labeled "Data Product ATO — System-Specific Controls," where the EM DPO is responsible only for product-level access approvals, schema definitions, and SLO configuration. An annotation across the diagram reads "60–70% of controls inherited by data product." The visual structure makes clear that the DPO does not navigate NIST compliance from scratch; the platform carries the majority of the burden, and the data product inherits security by virtue of being deployed on it.

### Diagram 6: Domain-Coupled Resource Hierarchy (Section 5.6, Model A)

**Caption:** Shows the GCP resource hierarchy when all workloads — data products, pipelines, applications, science environments, and HPC — are colocated within domain folders. Project names use the `n` convention to denote that each domain may operate multiple instances of each workload type.

**Walkthrough:** The diagram opens at the NOAA Fisheries GCP Organization node and drills down through a Domains folder into individual domain folders. Under Stock Assessment, five workload types sit side by side using generic project names: `data-product-n` (BigQuery, Data Catalog), `pipeline-n` (Cloud Dataflow, Cloud Composer), `app-n` (Cloud Run, GKE), `science-env-n` (Vertex AI Workbench), and `hpc-workload-n` (Batch, GPU). The same five-workload structure repeats under Fishery Monitoring, with `data-product-n` using BigQuery and Dataplex, and the remaining domains are summarized in a condensed sixth column. Each domain folder acts as a self-contained cloud estate — the DPO governs data products, pipelines, apps, science environments, and HPC resources from a single IAM context. Color-coded badges (DP blue, PL cyan, AP emerald, SC violet, HP amber) distinguish workload types across the legend. The `n` suffix, explained in a bottom caption, indicates that each domain may operate several instances of each workload category concurrently — a stock assessment domain might have multiple data products publishing survey indices and assessment model outputs simultaneously. The diagram makes the ownership coherence of this model immediately visible: every resource a domain needs lives in one place, under one team. It also reveals the classification challenge: confidential PII workloads and public data products share the same folder-level security perimeter, which forces the perimeter to accommodate the most restrictive classification.

### Diagram 7: Domain-Separated Resource Hierarchy (Section 5.6, Model B)

**Caption:** Presents the alternative resource hierarchy where data products remain in domain folders while pipelines, applications, science environments, and HPC workloads are separated by type into dedicated folders.

**Walkthrough:** The Organization node branches into seven top-level folders rather than the domain-centric structure of Model A. The Domains folder contains data products only — Stock Assessment, Fishery Monitoring, Protected Species, and the remaining five domains, each housing only their analytical data products. Separate folders hold Data Integration (pipeline projects), Applications (production and field apps), Scientific Computing (research environments), HPC and AI/ML (specialized compute), Platform (shared infrastructure), and Security (governance and audit). Cross-folder IAM arrows span the boundaries: Scientific Computing projects need read access to Domains projects for data consumption; Applications need access to both Domains and Data Integration. The Platform and Security folders sit at the bottom as shared infrastructure serving all folders. An annotation calls out that cross-folder IAM policies are required for integration. The diagram highlights the tradeoff: cleaner classification boundaries and distributed operational ownership, but at the cost of cross-folder IAM complexity and a fragmented ownership experience where a scientist publishing a data product works across two separate folders.

### Diagram 8: Legacy Migration Order of Operations (Section 6.2)

**Caption:** A five-step flowchart showing the application of the Anti-Corruption Layer, Strangler Fig, and Parallel Run patterns to migrate a legacy catch accounting system to the data mesh.

**Walkthrough:** The diagram is a vertical flowchart. Step 1 establishes the prerequisite: the platform foundation — Shared VPC, IAM, and templates — must be deployed before any migration work begins. Step 2 deploys the Anti-Corruption Layer: a Cloud Run REST API wraps the legacy Oracle database, presenting a clean, modern interface to consumers while the legacy schema remains untouched beneath. Step 3 applies the Strangler Fig pattern: new EM data is routed directly to BigQuery, but legacy queries still point to Oracle — consumers begin shifting incrementally. Step 4 is the Parallel Run: legacy Oracle and BigQuery run concurrently for an entire fishing season, their outputs compared to validate equivalence and build stakeholder confidence. Step 5 is decommissioning: all traffic is cut over to BigQuery, and the legacy Oracle system is retired. Steps 2 through 4 are grouped under a label "Migration Patterns Executed Within Fishery Monitoring Domain." Annotations between steps emphasize the incremental nature — "incremental redirection" between steps 3 and 4, "after validation equivalence demonstrated" between steps 4 and 5.

### Diagram 8b: Migration Data Flow — Consumer Perspective (Section 6.2)

**Caption:** A three-panel companion to Diagram 8 showing the consumer's experience of a data request before, during, and after migration — illustrating that the Anti-Corruption Layer provides a stable interface while the backend evolves from Oracle to BigQuery without disrupting consumers.

**Walkthrough:** The diagram is arranged as three side-by-side panels, each representing a migration phase from the consumer's perspective. In the "Before Migration" panel (neutral gray border), a Stock Assessment Scientist queries the Anti-Corruption Layer (ACL) on Cloud Run, which routes 100% of traffic to the Legacy Oracle database. The ACL provides a clean API but translates to legacy schemas underneath. In the "During Migration" panel (amber border), the scientist queries the same ACL, but now the ACL transparently splits traffic: queries for pre-migration historical data still route to Oracle, while queries for new or migrated data route to the BigQuery data product. The two backends sit side by side with labels "Data not yet migrated" and "Strangler Fig active," and the consumer sees no difference in their experience. In the "After Migration" panel (emerald border), all data has been migrated and validated through the Parallel Run pattern. The scientist still queries the same ACL, which now routes 100% of traffic to the BigQuery Data Product. Legacy Oracle appears dimmed and marked "Decommissioned." A legend across the bottom explains the color coding (blue = consumer, violet = ACL, rose = legacy, emerald = BigQuery) and drives home the key architectural message: the consumer experience never changes — always the same API — only the backend evolves underneath.

### Diagram 9: Current State Fragmentation (Section 2.1–2.2)

**Caption:** Visualizes the fragmented pre-mesh data landscape — siloed regional systems, multiple cloud platforms, and point-to-point integrations — to establish the problem the reference architecture is designed to solve.

**Walkthrough:** Reading left to right, six regional and programmatic systems appear as isolated database and storage nodes: Alaska FMC on Oracle, Northeast FMC on SQL Server, Pacific Islands on AWS, Southeast on Azure, Northwest on GCP, and Southwest on OCI. Each system sends its own independent arrow to a single consumer on the right — a Stock Assessment Scientist — but every connection is annotated with "manual extract, email request, personal relationship." There is no shared discovery layer, no standardized interface, no common quality framework. The systems are grouped under a shaded boundary labeled "Fragmented Regional and Programmatic Systems," and a callout at the bottom reads "No shared discovery, inconsistent schemas, redundant infrastructure." The scientist must know who owns what data in which region, navigate different access procedures for each system, and reconcile inconsistent schemas manually. The diagram establishes the baseline that the data mesh reference architecture is designed to replace.

### Diagram 9b: EM and ML Fragmentation (Section 2.1–2.2)

**Caption:** Zooms in on the EM and machine learning subdomain to show the specific fragmentation of AI/ML workflows, video processing pipelines, and data products across regions and cloud platforms.

**Walkthrough:** The diagram maps a more granular slice of the fragmentation shown in Diagram 9. Multiple regions appear as columns — Alaska, Northwest, Pacific Islands, and Northeast — each with their own EM video processing pipelines, ML model training environments, and data storage systems distributed across different cloud platforms and on-premises infrastructure. Video footage captured on vessels feeds into region-specific processing workflows; ML models for species identification are trained independently in each region on separate infrastructure; the resulting structured data lands in region-specific databases with no shared schema. Point-to-point arrows connect some regional systems where ad hoc integration has been established, but gaps are visible where no connection exists. The annotation emphasizes that the same species identification problem is being solved independently in multiple regions, with no shared training data, no common model registry, and no mechanism for one region to benefit from another's model improvements. This fragmentation is the specific problem that data products like the EM data product, served from a shared platform with unified governance, are designed to eliminate.

### Diagram 11: Four Principles Integration (Section 5.5)

**Caption:** A quadrant diagram showing how the four data mesh principles form a coherent system, with the EM Data Product at the center as their integrated result.

**Walkthrough:** The diagram is arranged as a 2×2 grid. In the top-left quadrant, Domain Ownership (Principle 1) describes how the Fishery Monitoring domain owns the full EM data product lifecycle, with the DPO coordinating a virtual team spanning six science centers. In the top-right, Data as a Product (Principle 2) specifies the EM Data Contract — schema v1.2, completeness above 99%, species accuracy thresholds, 30-day timeliness, and row-level access controls. In the bottom-left, the Self-Serve Platform (Principle 3) shows the Terraform template that provisions BigQuery, IAM, Data Catalog, Dataplex, and Cloud Monitoring automatically. In the bottom-right, Federated Computational Governance (Principle 4) enforces MSA confidentiality through row-level security and inherits 60–70% of NIST 800-53 controls via the platform ATO. From each quadrant, a colored dashed arrow points inward to a central circular hub labeled "EM Data Product as Integrated Whole." Bidirectional dashed lines connect adjacent quadrants with labels resolving the tensions between principles: between Domain Ownership and Data as a Product, "DPO owns product standards"; between Platform and Governance, "Policy defines platform templates"; between Domain Ownership and Platform, "Autonomy within guardrails"; between Data as a Product and Governance, "Contract-governed compliance." Diagonal rose-colored tension lines with italic labels — "Speed vs. Compliance," "Autonomy vs. Standardization," "Local vs. Global Consistency," "Speed vs. Security" — acknowledge that these principles exist in productive tension, not perfect harmony. The annotation beneath the diagram states the core argument: each principle addresses the structural weaknesses of the others, and the EM data product exists at their convergence.

### Diagram 12: Migration Phases and Dependencies (Section 6.1)

**Caption:** Shows the logical sequence of migration phases alongside the parallel organizational readiness track, with dependencies explicitly marked.

**Walkthrough:** The diagram flows left to right across two parallel tracks. The top track, labeled "Technical Migration," moves through five phases: Phase 0 deploys the platform foundation (Shared VPC, IAM, templates); Phase 1 deploys the Anti-Corruption Layer to wrap legacy systems; Phase 2 applies the Strangler Fig pattern for incremental feature migration; Phase 3 runs the Parallel Run for validation; and Phase 4 decommissions legacy systems. Arrows connect phases in sequence, with an annotation between Phases 2 and 3 reading "Iterative cycles per domain" — the migration is not a one-shot waterfall but a repeated pattern applied domain by domain. The bottom track, labeled "Organizational Readiness," runs three concurrent workstreams: Capability Building and Training, Organizational Change Management, and Governance Council Formation. Vertical arrows point upward from the readiness track to Phases 1 through 4, each labeled "Enables," making explicit that technical migration depends on organizational preparedness — you cannot deploy an Anti-Corruption Layer without trained domain teams, cannot redirect consumers without stakeholder buy-in, and cannot enforce governance without a functioning council.

### Diagram 13: Federated NOAA Enterprise Approach (Section 8.4)

**Caption:** A hub-and-spoke diagram showing four elements of pragmatic federation — standardized contracts, federated catalog, cross-cloud gateways, and a governance council — that connect the NMFS internal mesh to the broader NOAA enterprise without requiring all line offices to adopt a unified platform.

**Walkthrough:** The diagram reads top-to-bottom. At the top, a row of five line office cards — NWS, NMFS (highlighted with a blue border and "Internal Data Mesh" sub-label), NESDIS, OAR, and NOS — establishes the enterprise context: NOAA is composed of multiple autonomous organizations, each operating its own infrastructure, and NMFS is one participant among five. Dashed arrows fan downward from the highlighted NMFS card to four federation elements arranged in a horizontal row. Element 1, Standardized Data Product Contracts, defines cross-NOAA schema, quality metrics, and access controls. Element 2, the Federated Data Catalog, aggregates line office catalogs into a NOAA-wide discovery portal. Element 3, Cross-Cloud Data Access Gateways, implements the Cloud Broker pattern with policy enforcement, cost attribution, and cross-platform access routing. Element 4, the Enterprise Data Governance Council, provides a cross-NOAA standards body for reconciling statutory requirements. Cross-connection lines link Element 1 to Element 4 ("Policy defines contract standards") and Element 2 to Element 3 ("Catalog enables gateway routing"). Below the elements, a row of cloud platform containers — AWS, Azure, OCI, GCP — sits as a static reference layer, representing the heterogeneous infrastructure the gateways must bridge. The annotation beneath the diagram declares the framing: "This is a pragmatic federation, not a unified data mesh." The diagram conveys that NMFS can build its internal mesh independently while the four federation elements provide the connective tissue for enterprise-wide data sharing — each element adoptable independently as organizational readiness permits.
